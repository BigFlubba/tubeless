# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) and Codex (Codex.ai/code) when working with code in this repository.

## What this project is

Tubeless is a self-hosted Phoenix/Elixir web app that wraps `yt-dlp` to automatically download YouTube content (channels, playlists) on a schedule. It uses SQLite (via `ecto_sqlite3`), Oban for background jobs, and Phoenix LiveView for the UI. Deployed as a single Docker container with no external dependencies.

## Commands

> **On macOS, run tests through Docker, not natively.** The suite needs Linux-only
> binaries (SQLean `.so`, yt-dlp/ffmpeg/Deno/Apprise) that aren't available on the
> host, so `mix test` / `mix check` will not work directly. Use the two wrapper
> scripts below — they run inside the pinned ci-base image and share a warm build
> cache:
>
> - `tooling/test.sh [args…]` — **fast iteration loop.** Passes everything through
>   to `mix test`, skips the non-test checks and asset builds. This is what you run
>   after editing code.
>   - `tooling/test.sh test/path/to/file_test.exs` — one file
>   - `tooling/test.sh test/path/to/file_test.exs:42` — one test by line
>   - `tooling/test.sh --failed` / `--stale` — re-run last failures / affected tests
>   - `tooling/test.sh` (no args) — whole suite
>   - `tooling/test.sh --clean …` — wipe the cached volumes first
>   - `tooling/test.sh --shell` — drop into a shell in the container
> - `tooling/lint_test.sh` — **pre-commit gate.** Full `mix check` (compiler, credo, sobelow, prettier, full ExUnit) inside the same image. Slower; run once before committing, not while iterating. Shares volumes with `test.sh`.
>
> The bare `mix …` commands below are the underlying tasks these scripts run; on a
> Linux dev box (or inside `--shell`) you can call them directly.

```bash
# Initial setup
mix setup               # deps.get + DB create/migrate/seed + asset setup/build

# Development server (inside Docker or with deps installed)
iex -S mix phx.server  # starts on port 4008 in dev

# Tests
mix test                          # run all tests (creates/migrates DB automatically)
mix test test/path/to/file_test.exs          # single file
mix test test/path/to/file_test.exs:42       # single test by line number

# Full quality check (what CI runs)
mix check                         # formatter + compiler + sobelow + prettier + ex_unit

# Individual checks
mix credo                         # Elixir code style
mix sobelow --config              # security scan
yarn run lint:check               # Prettier (JS/CSS)
yarn run lint:fix                 # Prettier auto-fix

# Database
mix ecto.migrate                  # run migrations (also regenerates priv/repo/erd.png)
mix ecto.rollback                 # rollback one migration
mix ecto.reset                    # drop + recreate + migrate + seed

# Assets
mix assets.build                  # compile Tailwind + esbuild (dev)
mix assets.deploy                 # minified build + digest for production

# Versioning
mix version.bump                  # runs tooling/version_bump.sh
```

## Architecture

## Codebase

- Project layout is stored in @CODEBASE.md

### Core domain model

Two top-level entities drive everything:

- **`Source`** (`lib/pinchflat/sources/`) — a YouTube channel or playlist the user wants to track. Has a `MediaProfile` that defines download rules.
- **`MediaItem`** (`lib/pinchflat/media/`) — a single video/audio item belonging to a Source. Tracks download state, file paths, metadata.
- **`MediaProfile`** (`lib/pinchflat/profiles/`) — reusable settings for how to download (format, quality, naming, Shorts/livestream rules, SponsorBlock, etc.).

### Background job system

All async work is done through **Oban** jobs. There's a thin wrapper called **`Task`** (`lib/pinchflat/tasks/`) that links an `Oban.Job` to either a `Source` or `MediaItem`. Use `Tasks.create_job_with_task/2` when scheduling work — it handles deduplication and the task record atomically.

Key workers:

- `FastIndexingWorker` (`lib/pinchflat/fast_indexing/`) — polls YouTube RSS feeds to detect new videos quickly without hitting the API
- `MediaCollectionIndexingWorker` (`lib/pinchflat/slow_indexing/`) — full yt-dlp metadata fetch for a Source (slow indexing)
- `MediaDownloadWorker` (`lib/pinchflat/downloading/`) — downloads a single MediaItem via yt-dlp
- `MediaQualityUpgradeWorker` (`lib/pinchflat/downloading/`) — re-downloads media after a configured delay to get better quality
- `MediaRetentionWorker` (`lib/pinchflat/downloading/`) — deletes old media per retention settings
- `SourceMetadataStorageWorker` (`lib/pinchflat/metadata/`) — fetches and stores source-level metadata (images, NFO, etc.)
- `FileSyncingWorker` (`lib/pinchflat/media/`) — reconciles MediaItem records with files on disk
- `SourceDeletionWorker` (`lib/pinchflat/sources/`) — cascades deletion of a Source and all its media
- `MediaProfileDeletionWorker` (`lib/pinchflat/profiles/`) — cascades deletion of a MediaProfile
- `UpdateWorker` (`lib/pinchflat/yt_dlp/`) — keeps the yt-dlp executable up to date according to the configured update policy. The policy logic lives in `UpdateManager` (`lib/pinchflat/yt_dlp/update_manager.ex`): `stable`/`nightly` track a channel, `nightly_frozen`/`pinned` hold one version, and `nightly_until_stable` rides nightly then auto-reverts to stable once a stable release catches up (using `ReleaseLookup` against the GitHub API + `Utils.VersionUtils` for date-version comparison). The `stable` policy resolves the exact latest stable version via `ReleaseLookup` and targets `yt-dlp/yt-dlp@<version>` (not the `stable` channel) so yt-dlp will _downgrade_ when the installed binary is a newer nightly — a plain `--update` refuses to move backwards and would strand you on the nightly. If the GitHub lookup fails it falls back to the channel update. The one-shot jump on a settings change runs via `UpdateWorker.kickoff_apply/0` (`%{"apply_policy" => true}`), distinct from the recurring cron/boot run. The recurring run re-asserts the held version for `pinned` (`yt_dlp_pinned_version`), `nightly_frozen` (the captured `yt_dlp_nightly_baseline`, re-installed via the `nightly@<version>` target), and `nightly_until_stable` while it's still holding (re-installs the same `yt_dlp_nightly_baseline` nightly until stable actually catches up) rather than no-op'ing — yt-dlp lives on the container's ephemeral filesystem, so an image swap reverts it to the baked-in build and the policy must true it back up on boot. `CommandRunner.update/1` builds the actual yt-dlp target: an exact nightly pins via the `nightly@<version>` _channel alias_ (yt-dlp resolves `nightly` to the `yt-dlp/yt-dlp-nightly-builds` repo — naming a `yt-dlp/yt-dlp_nightly@<tag>` repo path fails), while stable/`pinned` versions pin via `yt-dlp/yt-dlp@<version>`. Note yt-dlp's exit codes here are counterintuitive: a no-URL update exits `0` for both a successful update and "already up to date", and exits `100` from its _error_ handler (bad/missing tag, network failure, unwritable binary) — so `update/1` treats only `0` as success. The policy is a DB setting (`yt_dlp_update_policy` / `yt_dlp_pinned_version`), edited in the Settings UI.

### yt-dlp integration

`lib/pinchflat/yt_dlp/` contains the yt-dlp abstraction. The executable path and runner module are injected via application config (`config :pinchflat, yt_dlp_runner: ...`), making it easy to mock in tests. In test, `config/test.exs` points both `yt_dlp_executable` and `apprise_executable` to scripts in `test/scripts/yt-dlp-mocks/`.

`ResponseDecoder` (`lib/pinchflat/yt_dlp/response_decoder.ex`) decodes JSON output from yt-dlp commands, logging the raw response and returning a clean `{:error, binary()}` tuple when it can't be parsed (empty/truncated output after an extractor or yt-dlp behaviour change). It's used by both `Media` and `MediaCollection` so workers fail-and-retry cleanly instead of crashing on `Jason.DecodeError`.

`UnavailableMedia` (`lib/pinchflat/yt_dlp/unavailable_media.ex`) classifies yt-dlp error output for media that can never be downloaded (members-only, private, removed). It's shared by the download path and the source-metadata/indexing path, and is kept distinct from the cookie-recoverable errors in `Downloading.MediaDownloader` so the cookie-retry path always runs first. When the `ignore_unavailable_media` setting is enabled, both paths treat these as permanently unavailable rather than failing/retrying.

SponsorBlock handling is configured per MediaProfile as two independent category lists (`sponsorblock_remove_categories` / `sponsorblock_mark_categories`), so a profile can remove some categories (e.g. sponsors) while marking others as chapters (e.g. intros). `Downloading.DownloadOptionBuilder.sponsorblock_options/1` emits `--sponsorblock-remove` and `--sponsorblock-mark` together, one per non-empty list; both lists empty means disabled. The changeset rejects a category appearing in both lists (yt-dlp would silently let remove win). The form's checkbox groups include a hidden empty input (in the shared `checkbox_group` component) so unchecking every box submits `[""]` — Ecto's cast filters the empty string, clearing the stored list.

Download format selection is built per MediaProfile by `Downloading.QualityOptionBuilder`. The `ignore_youtube_super_resolution` profile option is off by default; when enabled, every selected stream and fallback gets the yt-dlp filter `[format_note!*=?AI-upscaled]`. The `?` keeps formats without a `format_note`, while formats explicitly identified as YouTube Super Resolution are excluded. Keep the filter on every fallback branch when changing the selector so a trailing `best` cannot select an AI-upscaled format.

Proxy support is a global DB setting (`proxy_mode` = `none`/`manual`/`file`, plus `proxy_url` and the `proxy_covers_http` opt-in), edited in the Settings UI. `Pinchflat.Settings.Proxy` is the central resolver both the yt-dlp runner and the HTTP client consult: `resolve_url/0` reads live settings on every call (so a change takes effect on the next invocation, no restart), returning the manual URL in `manual` mode or a **randomly-picked-per-invocation** proxy from `proxy.json` in `file` mode. `proxy.json` is managed exactly like `cookies.txt` (`Pinchflat.Settings.ProxyFile` mirrors `CookieFile` — lives in `:extras_directory`, blank file created on boot by `PreJobStartupTasks`, empty ⇒ "no proxy"; the format is the list of `{host, port, protocol, username, password, …}` objects and `construct_proxy_string/1` ports the reference URL assembler, defaulting protocol to `http` and only emitting auth when a username is present). `CommandRunner.run/5` gets a `proxy_options/0` group (`--proxy <url>`) alongside the cookie/rate-limit/misc groups, so **every** network-using yt-dlp call is covered; `update/1` also prepends `--proxy` since the self-update reaches GitHub (`version/0` stays direct — local). The opt-in `proxy_covers_http` additionally routes Tubeless's **own** RSS-feed and YouTube-Data-API HTTP calls (which use Erlang `:httpc`, not Finch) through the proxy: since `:httpc`'s proxy is a profile-level option (not per-request), `HTTPClient` lazily starts a dedicated `:pinchflat_proxy` profile and sets its proxy per request, passing `proxy_auth` in HTTPOptions. **`:httpc` only ever connects to the proxy over plain TCP**, so `parse_http_proxy/1` accepts only `http` proxies — `https` (TLS-to-proxy) and SOCKS both return `{:error, :unsupported_scheme}` and fall back to a direct connection for the HTTP path (and can't be auto-tested by the Test button), while yt-dlp still honours all of them. The connectivity Test uses a **throwaway per-test `:httpc` profile** (unique name, stopped in an `after`) so keep-alive connections never leak one proxy's exit IP into the next test and the shared RSS/API profile is never mutated. The Settings UI groups everything in one "Proxy" box (colocated because the `proxy.json` uploader needs its own `<form>`, which can't nest inside the main settings form): `ProxyLive` is a **self-contained, self-saving** mini-form (mode select + manual URL with a **Test** button + coverage toggle) that **auto-saves** — like every section on the Settings page, it has no Save button and persists each field on change/blur via `Settings.update_setting/2`, showing inline validation errors and a transient "Saved" indicator (switching _to_ manual with no URL yet just reveals the field rather than saving an invalid required-URL state). Directly below it `ProxyFileLive` manages the file (upload/download/clear/test, like the cookies box). The Test button does a lightweight IP-echo GET (`proxy_test_url` config, default `https://api.ipify.org`) through the proxy and reports the exit IP.

### Other domain areas

- `lib/pinchflat/metadata/` — parses and persists yt-dlp metadata: source/media metadata, NFO files (for Jellyfin/Kodi), source images. Source-level NFOs/artwork are written to the source's "series directory", resolved by `SourceMetadataStorageWorker` from a simulated yt-dlp render of the output template: a `{{ series_root }}` marker in the template (expands to nothing in real renders; swapped for a sentinel during resolution) explicitly names the root directory, with a fallback that detects a season-style folder (`Season 1`, `s2024`, …) and uses its parent. The marker supports YouTube-style (`/Channel/Videos/…`) and flat layouts the season heuristic can't handle (issue #141); placement rules (one marker, attached to a directory name, not the filename) are enforced by `MediaProfile.validate_series_root_marker/2`, shared with `Source` for template overrides.
- `lib/pinchflat/podcasts/` — builds podcast RSS and OPML feeds so Sources can be consumed by podcast apps. Two delivery modes share the same builders (`RssFeedBuilder`/`OpmlFeedBuilder`) via pluggable URL strategies: **dynamic** (`DynamicFeedLinks`, the original behaviour — feeds and media streamed by Tubeless' own auth-bypassing endpoints) and **serve-in-place static** (`StaticFeedLinks` + `PodcastExport`) for users who won't expose Tubeless at all. The static mode does **not** copy media: podcast sources download _straight into_ the servable podcast library (`podcast_directory` config / `PODCAST_PATH`, default `<media dir>/podcasts`) under a readable per-source slug folder, and `PodcastExport` only writes the small generated artifacts alongside — `feed.xml`, `cover.<ext>`, and a root `opml.xml`. A dumb static web server points at `podcast_directory`. Enclosure/thumbnail URLs are each media file's real path relative to the library, URL-encoded (`StaticFeedLinks`); feed/cover live in `<slug>/`. Media files are owned by the download/retention system (they live here only because that's where they downloaded), so `PodcastExport` never copies, moves, or prunes them — only its own feed/cover/opml files. URLs are built from the required `podcast_url_base` setting (the external server's origin, which Tubeless can't know). Enablement is driven entirely by the `MediaProfile.podcast_enabled` toggle (audio vs video follows the profile's `preferred_resolution` — `:audio` makes an audio podcast); there is no per-source toggle. `Source.slug` is a stable, unique, human-readable name assigned on insert (`Sources.maybe_assign_slug`, suffixed on collision) and kept across renames so subscriptions don't break; sources predating the feature are backfilled by the `BackfillSourceSlugs` migration (a nil slug would otherwise flow into the output-path template parser and crash _every_ source's download/index path build, not just podcasts — `DownloadOptionBuilder` also `to_string`s the slug as a guard). Podcast sources download via a dedicated slug-rooted output template (`Sources.podcast_output_path_template/0`) and into `podcast_directory` (see `DownloadOptionBuilder.base_directory/1`) — for a podcast source this layout wins even over a `source.output_path_template_override`, since the static server and feed URLs depend on it. Media that isn't under `podcast_directory` (e.g. downloaded before the source became a podcast) is excluded from the static feed until it's re-downloaded, since its enclosure URL wouldn't resolve on the static server. Episode filenames are deliberately minimal (`{{ upload_yyyy_mm_dd }} {{ id }}.{{ ext }}` — titles live in the feed, and simple names make robust enclosure URLs). Regeneration is event-driven (debounced `PodcastExportWorker.kickoff/1` after downloads, deletions, relevant source/profile/settings edits) plus a daily `PodcastSweepWorker` cron reconcile that prunes generated feeds whose slug is no longer published (never touching media or unrelated directories).
- `lib/pinchflat/reconciliation/` — the file reconciliation ("true-up") feature: after path-affecting settings change (output path template, podcast toggle, `restrict_filenames`, sidecar toggles), a user-triggered dry run computes where every already-downloaded file _would_ land under the current settings and persists the result as a reviewable `ReconcilePlan` + `ReconcilePlanItem` rows (move/backfill/delete/skip/collision); a second confirming action applies it — media is never re-downloaded. The core trick (`PathPredictor` + `YtDlp.Media.predict_filepath_from_metadata/4`): each item's stored compressed metadata blob (written unconditionally on every download) is fed back to yt-dlp via `--load-info-json` with `--print`-style filename rendering against the current template, so path computation is **zero-network** (never the YouTube Data API, no indexing crawl) and yt-dlp itself applies `--restrict-filenames`/`--windows-filenames` sanitization; the rendered extension is replaced with the actual file's. `PlanBuilder` walks downloaded items (sidecars derive from the media rootname; source NFO/images relocate via an offline `series_root`-sentinel render — and when a source becomes a podcast, its now-orphaned series-level artifacts are deleted since podcasts have no series directory), flags collisions (duplicate targets, occupied target paths), and in `online`/`full` modes also plans network backfills (missing thumbnails/subtitles, light per-item yt-dlp fetches). Sidecars whose profile toggle is now off are **deleted** on apply (a true true-up — the UI warns; the internal metadata blob is never touched). Three modes: `local` (zero network), `online` (adds network backfills), and `full` (adds a forced media re-download — `MediaDownloadWorker` `force: true`, reusing the "Redownload Existing" path, runs after the reconcile window so it never races it) for items whose on-disk format no longer matches the profile; the mismatch is detected purely from the file extension (audio-vs-video, or container vs the profile's `media_container`/mp4 default) with no metadata parsing, since resolution/embed/sponsorblock state can't be judged reliably offline. `PlanApplier` executes per media item (cross-device moves fall back to copy+delete via `FSUtils.move_p/2`), skipping rows gone stale since planning, then updates the `*_filepath` columns and kicks `PodcastExportWorker`. Media-item groups are applied **in parallel** (`Task.async_stream`, `max_concurrency` = `reconcile_backfill_concurrency`, tied to `YT_DLP_WORKER_CONCURRENCY` at runtime) since each group is independent — keyed by `media_item_id`, ending in its own isolated DB write, with collisions already filtered out at plan time. This exists for the network-bound online/full backfills (thumbnails/subtitles), where a serial run of dozens of yt-dlp fetches can take 20+ minutes; the bound is kept low so a big reconcile doesn't hammer YouTube any harder than normal downloads. Concurrency `1` (the test config value) stays in-process via `Enum.each` rather than spawning Tasks, so the apply keeps the Ecto SQL sandbox connection; source-level rows always run serially after the media items. `ReconcileWorker` (queue `:local_data`, unique on worker+queue) runs both ops; **apply reserves a quiet window** exactly like `DatabaseMaintenanceWorker` (pause all queues, wait for executing jobs, resume in `after`). An apply interrupted by an ungraceful shutdown is **resumable**: `apply_plan` only touches rows still `:planned` and skips stale ones, so the apply `perform` clause accepts a plan in `:applying` (not just `:ready`) and finishes where it left off. Because `ReconcileWorker` is `max_attempts: 1`, such an interrupted job would otherwise be stranded — `PreJobStartupTasks.reset_executing_jobs/0` flips it `executing → retryable` already at its attempt ceiling (a stalled job Oban never re-fetches), leaving the plan stuck `:applying` forever and blocking new plans via the worker's uniqueness. `PreJobStartupTasks.revive_stalled_reconcile_jobs/0` (running right after `reset_executing_jobs/0` on boot) resets any stalled `ReconcileWorker` job to `available`/`attempt: 0` so Oban re-runs it and the apply auto-resumes; the diagnostics "Reset" remedy now works for it too since the guard no longer refuses a resuming plan. UI: the sidebar "Config" menu is now "Tools" with a "Reconcile" page (`/reconciliation`, `Settings.ReconciliationController` + `ReconcilePlanLive` paginated/filterable report table; the primary action is the "Scan and Build Plan" button); the source Actions dropdown links there pre-scoped. While a plan is applying the page shows a live "X of Y finished (Z%)" progress bar (`Reconciliation.apply_progress/1` counts applyable rows — move/backfill/delete/redownload — whose item status has left `:planned`); since a single long apply job fires no Oban `job:state` broadcasts, `ReconcilePlanLive` self-polls every 2s (`@poll_interval_ms`, guarded by a `tick_scheduled` flag) only while status is `:applying`, stopping once it isn't. A staged (ready) plan is marked stale — forcing a rebuild — when a Source, MediaProfile, or path-affecting global Setting (`restrict_filenames`) is saved (the Source/MediaProfile form controllers and the settings `MainSettingsLive` call `Reconciliation.mark_ready_plans_stale/0`), since those edits can change predicted paths.
- `lib/pinchflat/lifecycle/` — side effects around media lifecycle: Apprise `notifications` and user-defined `user_scripts` run via command runners.
- `lib/pinchflat/http/` — small HTTP client behaviour (`http_behaviour.ex` / `http_client.ex`) for RSS fetches and similar, mockable in tests.
- `lib/pinchflat/diagnostics/` — `QueueDiagnostics` powers the Oban queue diagnostics page in the UI. Each queue card on the page can be expanded to list the jobs currently in that queue (capped at 50, via `get_jobs_for_queue/2`); the Queue Health section is an embedded LiveView (`QueueHealthLive`, colocated in `diagnostics_html/`) so its Refresh button re-fetches stats in place instead of reloading the page. Discarded jobs can be reset or permanently deleted (`delete_discarded_job/1`), and a "Details" column resolves each job's args to the Source/MediaItem/MediaProfile it targets (`describe_job/2`). Long-running (executing) and retryable jobs can be **requeued** (`requeue_job/1`) rather than cancelled outright: this cancels the current run (killing its yt-dlp process if executing) and enqueues a fresh copy of the same worker + args at the back of the queue, re-linking it to a Task via `Tasks.create_job_with_task/2` when it targets a Source/MediaItem. This replaced a bare cancel that silently dropped the work — important for single-worker setups (`YT_DLP_WORKER_CONCURRENCY=1`) where a long slow-index holds the only slot and the user needs to yield it to other jobs without losing the index. A **"Stalled"** tab (alongside Retryable/Discarded/Orphaned) surfaces jobs that fall between the other checks: non-terminal jobs (`available`/`scheduled`/`retryable`, but not `executing`) that have reached `attempt >= max_attempts` (`get_stalled_jobs/1`). Oban's SQLite/Lite engine only ever fetches `available` jobs where `attempt < max_attempts`, so such a job is never picked up again and — never running — never discarded either; for workers with `unique: [states: :incomplete]` (several cron workers, e.g. `MediaRetentionWorker`) that stuck row also blocks every replacement from being enqueued, silently killing a recurring job. The canonical way in is a job that was `executing` during an ungraceful shutdown: `PreJobStartupTasks.reset_executing_jobs/0` flips it `executing → retryable` without recording an error or bumping the ceiling, and across repeated shutdowns its attempt count climbs to the ceiling. The **only** offered remedy is **Reset** (`reset_stalled_job/1` / `reset_all_stalled_jobs/0`): re-run the job by setting it to `available`, `attempt: 0`, errors cleared, `scheduled_at: now`. Re-running rather than discarding is deliberate — it's correct no matter what created the job (a cron job runs and frees its uniqueness lock; a self-perpetuating indexing job schedules its successor; a one-shot download just runs), whereas discarding would silently drop one-shot work that nothing re-creates. `attempt` is reset to **0, not 1**, so the fix holds even for `max_attempts: 1` workers like `ReconcileWorker`, where `attempt: 1` would still satisfy `attempt >= max_attempts` and leave the job stuck. Both reset functions scope their `UPDATE` to the stalled predicate, so a job that changed state since the page rendered matches nothing (no resetting a job that's legitimately running). The page also has a "Database" section powered by `DatabaseDiagnostics`: on-disk size broken into the main file vs the WAL/SHM sidecars (the two are summed, which is why the UI figure exceeds an `ls` of the main file), VACUUM-reclaimable space (`freelist_count × page_size`), journal mode, row counts for the growth-dominating tables, and an orphaned-tasks canary (tasks whose Oban job vanished — should always be 0 since the FK cascades). A "Check Integrity" button next to "Compact Now" runs `DatabaseDiagnostics.run_integrity_check/1` (`:quick` → `PRAGMA quick_check`, `:full` → `PRAGMA integrity_check`) and reports SQLite's findings verbatim in a modal. Both pragmas are read-only and take only a read transaction, so in WAL mode they never block writers — no quiet window is reserved and jobs keep running; the only cost is the I/O of reading every page. Since SQLite 3.44 they also invoke each virtual table's `xIntegrity` method, so FTS5 damage to `media_items_search_index` is reported alongside ordinary b-tree corruption. The feature is deliberately **report-only**: repairs (`INSERT INTO media_items_search_index(media_items_search_index) VALUES('rebuild')` for the search index, restore-from-backup for real table corruption) depend on what's damaged and are safest with the app stopped, so they stay a manual documented procedure rather than a button. It's an embedded LiveView (`IntegrityCheckLive`, colocated in `diagnostics_html/` like `QueueHealthLive`) rather than a plain POST because a full check on a large database can outlast the HTTP request timeout — the check runs in the LiveView process behind a spinner, so it reads as synchronous without a request hanging. Findings are ephemeral (socket state, not persisted) since re-running is one click. Note that a repair applied from another connection while the app is running does **not** clear the in-app finding — the existing pool connections keep reporting the old corruption until a restart (SQLite caches FTS5 index state per connection), which is the practical argument for repairing with the app stopped. Tests fabricate genuine corruption by zeroing the block column of the FTS5 shadow table (`media_items_search_index_data`) via the shared `corrupt_search_index/0` test helper, which SQLite permits and which rolls back with the sandbox transaction. The helper forces an FTS5 `rebuild` first — FTS5 buffers index writes in memory, so without that flush the shadow table may have nothing to corrupt and the test silently passes against an intact index. Database compaction runs through `DatabaseMaintenanceWorker` (WAL `wal_checkpoint(TRUNCATE)`, then `VACUUM` + `PRAGMA optimize`, then a final checkpoint-truncate — in WAL mode the VACUUM commits the rebuilt database through the WAL, which would otherwise balloon to the size of the database and distort the reclaimed-bytes figure), triggered by the "Compact Now" button (user-facing copy says "compact", not "vacuum") and a monthly cron (1st of the month, 03:00, after the retention/quality-upgrade jobs so their deletions are reclaimable). Scheduled runs are **opt-in** via the `database_maintenance_enabled` setting (default off while the feature matures — intended to flip to opt-out later): a disabled scheduled run cancels with a reason that the diagnostics card surfaces, while the button always runs regardless (it enqueues with `%{"manual" => true}`, mirroring `UpdateWorker.kickoff_apply/0`'s pattern; job uniqueness is scoped to worker+queue so manual and cron runs still dedupe against each other despite differing args). VACUUM holds the write lock for its whole run — minutes for a ~1GB database on Pi-class hardware — so the worker first reserves a quiet window: it pauses all Oban queues, waits indefinitely for other executing jobs to finish (a slow index can take hours; poll cadence via the `db_maintenance_poll_interval` config), then vacuums and resumes the queues in an `after` block (pause state is in-memory, so a crash can't leave queues stuck paused). As a second line of defense the Repo sets `busy_timeout: 30_000` so writes that do collide with a slow operation wait instead of failing with "database is locked". Inside the reserved window it verifies the DB and temp directories have free space for a full temporary copy of the database (checked via the `disk_space_checker` config, a `df`-backed behaviour mocked in tests) and fails with a descriptive error otherwise — failures surface both in the Failed Jobs tables and in the card's "Last maintenance run" line, which reads the most recent worker job record (including reclaimed bytes stored in the job's `meta`) so silent cron runs are still auditable.

### Indexing: fast vs slow

Tubeless uses two indexing strategies:

1. **Fast indexing** (`lib/pinchflat/fast_indexing/`) — parses YouTube's RSS feed to detect new video IDs cheaply and frequently, then schedules individual downloads.
2. **Slow indexing** (`lib/pinchflat/slow_indexing/`) — runs full yt-dlp collection fetches on a longer schedule to catch anything RSS misses and update metadata. YouTube channels are indexed one content tab at a time (`/videos`, `/shorts`, `/streams` — canonical URLs built from the source's `collection_id`) as separate yt-dlp invocations, each with its own download archive filtered to that tab's content type. This is required because `--break-on-existing` aborts the whole yt-dlp process, not just the current tab — a single bare-channel-URL run with an archive would stop at the first known video and never reach the shorts/streams tabs (issue #59). A channel URL that already names a tab is used as-is; playlists and non-YouTube sources are never split. A tab that errors (e.g. the channel has no shorts tab) is skipped; the run only fails if every tab fails. A source can also set an **indexing cutoff date** (`index_cutoff_date`): each channel tab then gets `--break-match-filters` so yt-dlp aborts the crawl once it reaches videos uploaded before that date — this applies to first/forced indexes too (where the download archive doesn't), which is where it saves the most time on large channels. It's only applied to YouTube channel tabs (newest-first ordering is what makes the early abort safe); playlists and non-YouTube sources ignore it. A paired `!upload_date` filter keeps date-less entries (upcoming premieres) from tripping the break, and the changeset rejects an index cutoff after the source's download cutoff (media between the two could never be indexed, hence never downloaded).

### Boot sequence

`lib/pinchflat/boot/` has three GenServers run at startup:

- `PreJobStartupTasks` — runs before Oban starts: resets stuck `executing` jobs to `retryable`, revives stalled `ReconcileWorker` jobs (so an apply interrupted by a shutdown auto-resumes instead of deadlocking its plan in `:applying`), ensures the tmpfile directory and blank cookie/yt-dlp-config/user-script files exist, records the installed yt-dlp/Apprise versions, and runs the `app_init` user script
- `PostJobStartupTasks` — runs after Oban starts: re-kicks any missing indexing job chains. Slow/fast indexing jobs are self-perpetuating (each run schedules its successor), so if a job exhausts its retries and is discarded the chain dies — this reconciliation revives it on the next boot without double-scheduling live chains
- `PostBootStartupTasks` — runs once everything is ready (triggers yt-dlp self-update)

All three use `restart: :temporary` so they run once and exit cleanly.

### Offline database maintenance mode

Setting `MAINTENANCE_MODE` (`1`/`true`/`yes`/`on`) makes `rel/overlays/bin/docker_start` `exec` into `rel/overlays/bin/maintenance_mode` before doing anything else — the permissions check, the migrator, and the release itself are all skipped, so the BEAM never starts and nothing opens the SQLite file. This is for operator work on the database file from outside the app (backup, restore, hand-repair); routine compaction is the online `DatabaseMaintenanceWorker` path instead. The container idles under a small `maintenance_server.py` listener that answers **200 on every path** (JSON on `/healthcheck`, an explanatory HTML page elsewhere) so the Docker `HEALTHCHECK` and k8s probes keep passing while the app is down — it deliberately never returns 503, since a probe pointed at a non-health path would then fail and restart-loop the pod. It falls back to a signal-trapping idle loop if `python3` is somehow missing. The maintenance commands (`db_backup`, `db_check`, `db_shell`) are plain `sqlite3` shell scripts with no BEAM involvement, sharing `db_common.sh` which resolves the database path the same way `config/runtime.exs` does. `db_backup` takes a **raw binary** backup — a zstd-compressed tar of the database file plus its `-wal` sidecar (the `-shm` is a derived scratch index SQLite rebuilds, so it's deliberately excluded). It deliberately does _not_ go through SQLite's engine (`VACUUM INTO`, `.backup`, `.dump`): those refuse to read a corrupt file, which is exactly when a copy matters most. The source's integrity is checked and reported _after_ the archive is written, and **never** causes it to be discarded — a faithful copy of a damaged database is the whole point of backing one up before a repair. Full operator docs are in DEVELOPMENT.md.

### Web layer

Standard Phoenix with LiveView. Routes are defined in `lib/pinchflat_web/router.ex`. The web layer is organized by resource under `lib/pinchflat_web/controllers/` (sources, media_items, media_profiles, settings, podcasts, searches, pages) with shared UI in `lib/pinchflat_web/components/`. LiveViews are colocated with their controllers as `*_live.ex` files (e.g. `sources/source_live/`, `settings/setting_html/cookie_file_live.ex`) rather than living in a separate `live/` directory. Notable routing details:

- Podcast RSS/OPML endpoints bypass basic auth intentionally (to work with podcast apps)
- `/healthcheck` bypasses auth and CSRF
- `strip_trailing_extension` plug in `endpoint.ex` allows media streaming URLs with extensions
- 404/500 error pages render through a dedicated standalone layout (`components/layouts/error.html.heex`, set as `render_errors` `root_layout`) — deliberately free of flash, LiveView, and `Settings.get!` DB calls so error rendering can't crash again mid-render (the app/root layouts require assigns and DB access the error conn doesn't have)
- `Plug.Static` in `endpoint.ex` pairs `only:` with `only_matching: ~w(favicon apple-touch-icon)` because `~p` emits digested filenames in prod that a literal `only:` match would reject (sending every browser icon request through the router as a 404)
- The source **artwork route** (`GET /sources/:id/image/:image_type`, `SourceController.image/2`) serves a source's banner/poster/fanart from disk. Two layers keep it from becoming an arbitrary-file-read: (1) the app-managed filepath columns (`series_directory`, `nfo_filepath`, `poster/fanart/banner_filepath`) are **not** in `Source`'s public `@allowed_fields` — they live in `@internal_fields` and are cast only when a caller passes `cast_internal_fields: true` to `Sources.update_source/3` (the metadata storage worker and the reconcile plan applier; HTTP updates can't set them, which also blocks arbitrary-file-**delete** via the source-deletion filepath sweep); and (2) `image/2` still refuses to serve anything that isn't a regular file canonically under `media_directory`/`metadata_directory`. Keep both when touching either.
- The header **status pill** (`Sources.status/1`) is `:paused` when disabled, else `:error`/`:active`. `:error` means the latest indexing job **of either indexing chain** is retryable/discarded, OR the latest download job for any of the source's media items is retryable/discarded (download tasks attach through `media_item_id`, not `source_id`, so the query joins `media_items`; "latest per target" keeps a stale discarded job from painting a recovered source red until Oban prunes it 30 days later). Indexing health is grouped **per worker**, not taken as one global latest job: fast (RSS) and slow (yt-dlp) indexing are independent self-perpetuating chains, so a successful fast index must not vouch for a dead slow-indexing chain, or vice versa. Source actions that would re-create the job chains pausing removed (`check_for_new_videos`, `force_index`, `force_download_pending`, `force_redownload`) refuse to run on a disabled source (`require_enabled` in `wrap_forced_action`). The header's **Check for new videos** button goes through `SlowIndexingHelpers.kickoff_incremental_check/1`, which — unlike `kickoff_indexing_task/3`, used by the full rebuild — **never cancels an index that is already executing**: it returns `{:error, :already_running}` and `wrap_forced_action` flashes that instead, since killing an hours-deep crawl to restart the same incremental crawl is pure loss (and contradicts the `:index_pending` banner telling the user to wait). Waiting jobs are still replaced. Tab selection reads the `#tab-<id>` hash (`assets/js/tabs.js`); `tabbed_layout/1` passes it the page's tab ids so a hash naming a tab that doesn't exist (a stale link, a renamed tab) falls back to the default instead of hiding every panel.
- Flash messages render as **auto-dismissing top-right toasts** (`CoreComponents.flash_group/1` is `fixed` top-right; each real info/error flash gets `autodismiss` → Alpine slide-in + 5s fade-out via `toast_dismiss_attrs/1`). The `client-error`/`server-error` connection flashes are **not** auto-dismissed so they persist while the socket is down.
- The source page's tabs are counted by `Sources.tab_counts/1` (`%{pending, library, skipped, library_bytes}`, one round trip and **one pass** over the source's media — conditional `SUM(CASE WHEN … )` aggregates, not a union of three counts, which would read the rows three times), and each count uses the exact predicate of the tab it labels so a badge can never disagree with its list. The first tab is named **Pending**, not "Queue": the count is `MediaQuery.pending/0`, an _eligibility_ predicate that says nothing about whether an Oban job exists — an item counts while `download_media` is off, or after its job was cancelled or pruned. Per-row "Queued"/"Downloading" state is the separate `MediaQuery.in_download_queue/0` / `downloading/0` pair, which does look at jobs. Keep the wording honest if these ever diverge again.
- The source page's **Skipped tab** (the `MediaItemTableLive` `"other"` media state — items neither downloaded nor pending) names _why_ each item was skipped. `Pinchflat.Media.SkipReason` (`lib/pinchflat/media/skip_reason.ex`) is the pure, unit-tested **spec**: `reason/2` decomposes the same predicates as `MediaQuery.pending/0` into a fixed-precedence reason atom (`:unavailable` → `:removed` → `:ignored` → `:before_cutoff` → `:format_excluded` → `:title_filter` → `:too_short` → `:too_long` → `:filtered`), and `for_media_item/2` adds a label/icon/class plus a concrete "why" string (e.g. "2:00 is under the 10:00 minimum"). The row chip derives this per-row from the loaded records (cheap — pagination already caps rows), so `source.media_profile` must be preloaded (mount does this) and `select_fields/0` must select the fields it reads (`short_form_content`, `livestream`, `duration_seconds`, etc.). The **reason filter dropdown** (only on the Skipped tab) is backed by `MediaQuery.skip_reason_is/1`, whose clauses mirror `SkipReason.reason/2`'s precedence one-for-one (each is "fails this predicate AND passes every higher-precedence one") so the filter and the chip can never disagree — a shared test constructs one item per reason to lock them together. The SQL clauses are deliberately NULL-safe on `duration_seconds` (an item with no recorded duration is neither too short nor too long, matching `SkipReason`; without the explicit `is_nil` guards the negations in `:filtered` would go NULL and such an item would match no reason at all). The filter is applied as a DB `where` (so pagination stays in SQL) via a `filter_reason` LiveView event, matching the existing (non-URL-driven) search box pattern rather than reflecting into the URL.

- The source page's **Details tab** (`sources/source_html/details_tab.html.heex`, a function component of `SourceHTML`) replaced the old `Raw Attributes` map dump. `SourceHTML.info_groups/1` is the single definition of what it shows: four groups (Identity, Indexing, Filters, Storage) of `%{label, value, help, type, href, tooltip}` field maps, where `value` is already a **display string** (`Daily (recommended)`, `2:00`, `30 days`, `Yes`/`No`) so the template never formats. A field is "unset" per `field_set?/1` (blank/nil string); unset rows — and a group whose fields are all unset — stay in the DOM but render `display: none` and are revealed by the Alpine `Show unset fields` toggle, so no round trip is needed. `type` picks the renderer (`:url`, `:code`, `:long`/`:long_code` get an Alpine line-clamp expander, `href` makes it a link with the media-profile summary on hover). App-managed identifiers and filepaths moved to `internal_fields/1` in an always-expanded `Internal` box whose header carries a `Fields`/`Raw JSON` segmented control (`source_json/1` renders the same payload as `Copy JSON`). The tab is **read-only** — editing stays on the `/sources/:id/edit` form reached from the header, and the delete actions stay in the header's Actions dropdown. `SourceHTML.switch/1` and `segmented_control/1` are local, purely client-side controls bound to an Alpine expression (no form field behind them, unlike `CoreComponents.input type="toggle"`).
- The source page's **blocking-conditions banner** answers "why is nothing downloading?" in one line above the tabs. `Sources.blocking_conditions/2` is the spec: an **ordered** list of `%{code, message}` for everything standing between the source and a downloaded file (`:downloads_disabled` → `:indexing_failed` → `:index_pending`/`:never_indexed`/`:index_found_nothing` → `:cutoff_excludes_everything`/`:all_filtered_out` → `:queue_paused` → `:storage_directory_unwritable`), **empty for a healthy source** — there is deliberately no `:all_good` code and the UI shows no green "all clear" bar. A **paused source returns `[]`** from the first clause: being paused is a chosen state the header pill already reports, and everything downstream of it is a consequence rather than a cause. `:indexing_failed` is ranked **above** the nothing-indexed conditions because it explains them — a failing first index would otherwise be reported as "being indexed, please wait" or "hasn't been indexed yet", hiding the actual error behind its symptom (both `:index_pending` and `:never_indexed` are suppressed while it's set). `:index_pending` (nothing indexed yet but an indexing job is `available`/`scheduled`/`executing`/`retryable`) is split out from `:never_indexed` precisely so the banner does **not** offer a "check for new videos" button on a freshly-added source — creation kicks off the first index, so that button would only enqueue a duplicate of the job already on its way. `SourceHTML.blocking_banner/1` renders only the **first** entry (fixing the most fundamental one may clear the rest) plus a `condition_action/2` link to the control that resolves it (nil for conditions with nothing actionable — `:index_pending`, `:storage_directory_unwritable`); routes live in the web layer, not the context. `condition_severity/1` tints the banner: `:danger` for something broken, `:info` for working-as-intended-but-not-obvious (`:index_pending`, `:queue_paused`), `:warning` for a chosen setting with an unintended consequence. The two conditions that probe outside the database — the Oban `media_fetching` queue's paused state and the storage directory's mode bits — are injectable via `opts` (`:queue_paused?`, `:storage_directory_writable?`). The storage directory is the one this source actually downloads into: `podcast_directory` for a podcast-publishing source (often a separate volume), `media_directory` otherwise, matching `DownloadOptionBuilder.base_directory/1`; they keep the function pure under test, and `download_queue_paused?/0` treats an unanswerable `Oban.check_queue` (test env, no running queues) as "not paused" rather than as a block. `tab_counts` is passed in from the controller so the banner costs no extra count query, and `everything_before_cutoff?/2` reuses `MediaQuery.skip_reason_is(:before_cutoff)` so the banner can't disagree with the Skipped tab's per-row reason.
- The source page's **Activity tab** (`sources/source_html/activity_tab.html.heex`) is a timeline of recent and in-flight work, replacing the old three-column table of raw worker module names and job states. `Tasks.list_recent_activity_for_source/2` is the query: the source's own tasks **plus its media items' tasks** (downloads attach through `media_item_id`, not `source_id`), ordered by `COALESCE(completed_at, cancelled_at, discarded_at, attempted_at, scheduled_at, inserted_at)` desc so scheduled and executing work sorts above finished history, and **bounded by a limit (default 50)** — never an unfiltered `oban_jobs` scan. The `tasks`-side filter is a **UNION of the source's own task IDs and its media items' task IDs**, not an `t.source_id = ? OR media_items.source_id = ?` disjunction — the OR form defeats both `tasks_source_id_index` and `media_items_source_id_index` and degrades into a full scan of `tasks` that the LIMIT can't rescue (the scan and sort happen first). `SourceHTML.activity_entry/1` turns each task into display-ready values (plain-language worker label + icon, status chip, wall-clock duration, attempt counter, latest error). The failures are a **separate query** (`Tasks.list_unresolved_activity_for_source/2`) rather than a filter over the capped timeline, so a failure that 50 newer successful jobs have pushed out of the window still pins above the timeline. It reports only work that is failing **now**: rows are grouped per `{worker, source or media item}` and only each group's latest job counts, and only if it is `retryable`/`discarded` — the same "latest per target" rule as `Sources.status/1`, so a re-run that succeeded clears the badge instead of leaving it red until Oban prunes the discarded job 30 days later and still drives the **danger-tinted `error_count` badge** on the tab label (a second optional badge added to the shared `TabComponents.tabbed_layout/1` tab slot, alongside the neutral `count`, which is `Tasks.count_in_flight_activity_for_source/1` — in-flight jobs across both the source's own and its media items' tasks). Errors split via `error_summary/1` into an on-screen headline and an expandable detail, since yt-dlp failures arrive as multi-line blobs. **No Oban config change was needed** for history: `Pruner` is already `max_age: 30 * 24 * 60 * 60`, and the `tasks` FK cascade drops task rows with their pruned jobs, so the window self-bounds at 30 days. Job-level remedies (retry/requeue/discard) intentionally stay in Tools → Diagnostics rather than being duplicated per-source.
- The source page's **Podcast tab** (`sources/source_html/podcast_tab.html.heex`, sitting to the right of Details) presents **both** delivery modes side by side as `SourceHTML.feed_option/1` rows: the **dynamic** feed Tubeless serves itself (`rss_feed_url/2` → `/sources/:uuid/feed.xml`, always available, hence listed first and badged Ready) and the **static** feed an external web server serves (`static_podcast_feed_url/1`). Each row is what-serves-it + why-you'd-use-it + a click-to-copy URL field; a feed that isn't usable yet renders an `:unavailable` slot instead of the URL, covering both blocked states (`podcast_url_base` unset / export still pending), so the row is never just missing. The tab renders for **every** source, not just publishing ones — the dynamic feed route works for any source regardless of `podcast_enabled`, so gating the tab would hide a feed that already exists. `SourceHTML.podcast_source?/1` (`PodcastExport.enabled?/1`) now only decides the static row's state: a non-publishing source gets an `:unavailable` block pointing at its media profile's `Publish as Podcast` toggle. The on-disk publish path is shown only once a static feed exists or is pending, since it's meaningless otherwise.

- The **media profiles index** (`/media_profiles`) is a LiveView table (`media_profiles/media_profile_live/index_table_live.ex`) built like the sources index: sortable headers, pagination, and the shared `.table` density. It deliberately has **no per-page selector and no filter dropdown** (the sources index has both) — installs have a handful of profiles, not hundreds, so those controls would be clutter. The controller's `index` action just renders the shell — the query lives in the LiveView. Alongside Name it shows the profile's **effective download settings** (`Quality` — friendly resolution label with the container underneath, defaulting to `mp4 (default)` for video profiles that set none, matching what the reconcile format check assumes; `Content` — a plain-language summary of the Shorts/livestream behaviours whose clauses mirror `MediaQuery.format_matching_profile_preference/0`'s precedence one-for-one, so `:only` wins over the other field's `:exclude` and both-`:only` reads as a union ("Shorts and livestreams only"), not an intersection; `Extras` — chips for the enabled sidecars/SponsorBlock, where the Subtitles chip follows what `DownloadOptionBuilder.subtitle_options/1` actually emits rather than "a subtitle checkbox is ticked" (`download_auto_subs` alone emits nothing, and `embed_subs` is skipped for audio profiles); `Podcast?`) plus **aggregates across every source using it** (`Sources`, `Downloaded`, `Size`, each sortable via `LEFT JOIN` subqueries so profiles with no sources still render as 0). Quality sorts by a `CASE` rank (8K → audio), not the enum's alphabetical string order. Pagination counts run against a **bare `MediaProfile` query**, not the aggregate one — `Repo.aggregate/3` only swaps the select and keeps the joins, so counting through the display query would materialize both grouped subqueries (a full pass over `media_items`) on every mount and page change. `sort_update` resolves its payload against a known-sortable list instead of `String.to_existing_atom/1`, so a hand-crafted sort key is ignored rather than crashing the LiveView.

- The **media profile detail page** (`/media_profiles/:id`) mirrors the source detail page's shape: an identity header (gradient band, name, a Podcast badge, the profile's extras as chips) over a four-cell metric strip (`Sources`, `Downloaded` + size, `Quality`, `Content`), with Edit and the Actions dropdown moved out of the tab bar and into the header, then two tabs — **Details** (default) and **Sources**. Details replaced the old `Map.from_struct` dump: `MediaProfileHTML.info_groups/1` is the single definition of what it shows (Quality, Content, Subtitles, Extra files, SponsorBlock, Output), returning `%{label, value, help, type}` field maps whose `value` is already a display string, with the same unset-field hiding, `Show unset fields` switch, line-clamp expander, and `Fields`/`Raw JSON` Internal box as the source page. The plain-language summaries (`resolution_label`, `container_label`, `content_label`, `extras_labels`) live in `PinchflatWeb.MediaProfiles.MediaProfileSummary`, shared with the index table so the two pages can't describe one profile differently, and the Alpine-only `switch/1` + `segmented_control/1` controls moved from `SourceHTML` into `CustomComponents.ButtonComponents` for the same reason. Details also carries an **Effective yt-dlp options** panel — the download path (the profile's template joined to `DownloadOptionBuilder`'s base directory, since a bare template reads as relative to nothing; podcast profiles instead show the slug-rooted podcast-library layout and say the template is ignored, and a caveat line counts the sources whose `output_path_template_override` wins over it — always zero for a podcast profile, since `Sources.output_path_template/1` checks `podcast?` _before_ the override, so such a source downloads into the podcast library regardless of what its override says) plus the flags this profile contributes to every download, rendered from `DownloadOptionBuilder.build_profile_options/1` (the profile-only subset of `build/2`: subtitles, thumbnails, metadata, quality, SponsorBlock — no output paths, thumbnail _destination_, or config file, which need a media item; `thumbnail_options/1` was split so the profile-determined flags have one definition rather than a second drift-prone copy, and a test asserts the preview is a strict subset of a real `build/2`) so the preview can't drift from what a real download passes. The Sources tab adds a per-row status pill and downloaded count/size; the pill's health comes from `Sources.failing_source_ids/1`, the batched form of `Sources.status/2`'s "latest job per target" rule (two queries for the whole table, not two per row), and the counts from one `LEFT JOIN` over a grouped subquery resolved in the controller, with the header strip rolled up in Elixir from those same rows. That subquery is **inner-joined to `sources` and scoped to this profile** (and to sources not marked for deletion, matching the index): an outer `media_profile_id` filter can't constrain a grouped subquery, so without it opening one profile would materialize an aggregate over every downloaded item in the library.

The **Settings page (`/settings`) has no Save buttons — every field auto-saves.** `SettingController` only renders the shell (`show`) and serves file downloads (cookies/proxy/logs); there is no `update` action or `PUT /settings` route. `show.html` owns the **card layout** — seven task-oriented cards (Appearance, Connection, Credentials and Access, Media Output, Library, Integrations, System) — and composes each card from LiveViews rather than one big form. The plain (non-file) fields live in `MainSettingsLive` (`settings/setting_html/main_settings_live.ex`), which is **`live_render`ed once per card with a `%{"section" => …}` session** and pattern-matches that section in `render/1` to emit only that card's `<form>` (so the same module supplies the Throttling fields under Connection, the API key under Credentials, codec+restrict under Media Output, the `table_density` selector under Appearance, etc.). The Appearance card holds pure UI-display preferences; `table_density` (`compact`/`normal`, default `compact`) drives the shared `.table` component's row spacing — the component resolves its `density` from this setting when a caller doesn't pass one explicitly (see `TableComponents.table/1`), so every data table honours it app-wide. Each instance is an independent root LiveView (siblings of `ProxyLive`/`CookieFileLive`, not nested), and since the sections own disjoint fields there's no cross-instance staleness. It persists each field via `Settings.update_setting/2` on `phx-change` (selects/toggles fire immediately, text/number debounce on blur), keying off the change event's `_target` so only the edited field is written — except the yt-dlp `update_policy`/`pinned_version` pair, which saves as a group so a transiently-invalid "pinned with no version yet" state just reveals the field instead of erroring. Invalid input keeps the typed value visible with an inline error and leaves the stored value untouched; on success only the just-saved field is re-read (so a neighbouring field's in-progress edit isn't clobbered). **Save confirmation is per-field and inline, uniformly across the whole page: a text/number input flashes a transient "Saved ✓" appended _on the field itself_** (`<:input_append>`); toggles and selects show nothing, since flipping/picking already leaves the new value visible. This rule is applied everywhere — the proxy URL (text) gets the inline check while the proxy mode (select) and coverage (toggle) and the default-cookie-behaviour (select) do not — so there are no free-floating form-level "Saved" chips to mis-position. `MainSettingsLive` folds in the Apprise / YouTube-API / yt-dlp-version **Test** buttons that previously lived in their own embedded LiveViews (there is **no Standard/Advanced editing-mode toggle** anymore). The yt-dlp one-shot policy apply (`UpdateWorker.kickoff_apply/0`) and reconcile-plan staleness (`Reconciliation.mark_ready_plans_stale/0`, only when `restrict_filenames` changed) fire from its save path, not the controller. `ProxyLive` (Connection card, with `ProxyFileLive`) and `DefaultCookieBehaviourLive` (Credentials card, with `CookieFileLive`) are likewise buttonless self-saving LiveViews; the cookie/proxy **file** boxes keep their upload/clear action buttons (those are file actions, not setting saves). `download_throughput_limit` is validated (`\d+(\.\d+)?[KMG]?`) so a typo surfaces inline at edit time rather than silently failing at download.

### Configuration injection pattern

Executables and pluggable backends are stored in application config and read at runtime, not hardcoded. This means tests override them cleanly via `config/test.exs`. When adding new external tools or swappable backends, follow this pattern rather than calling executables directly.

## Writing conventions

- **User-facing text is American English.** Flash messages, UI copy, error strings, tooltips, button labels, and anything else a user reads in the app use American spelling (`color`, `behavior`, `favorite`, `license` as a verb, etc.), not British/Commonwealth spelling. This applies to strings in `lib/pinchflat_web/` (templates, LiveViews, components) and `priv/gettext/`. It does not apply to code identifiers, comments, or internal docs (CLAUDE.md, CODEBASE.md, DEVELOPMENT.md) that predate this rule.
- **Never use real YouTube video or channel links/IDs**, in code, tests, docs, or examples — not even as placeholders. Use fake, made-up values that match YouTube's URL syntax instead, e.g. `https://www.youtube.com/watch?v=aaaaaaaaaaa`, `https://www.youtube.com/@some-fake-channel`, `https://www.youtube.com/playlist?list=PLxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`. This keeps the repo from linking to real people's content and avoids tests/docs going stale if a real video is deleted or renamed.

## Commits and releases

Use [Conventional Commits](https://www.conventionalcommits.org/):

- `fix:` → patch release
- `feat:` → minor release
- `chore:` / `docs:` / `perf:` / `revert:` / `style:` / `refactor:` / `test:` / `ci:` → no release bump

Only `fix:`, `feat:`, and a `!` / `BREAKING CHANGE:` (major) bump the version. Every type above is recognized by release-please (see the `changelog-sections` in `release-please-config.json`) and is sorted into the changelog accordingly — `test:` and `ci:` are hidden. Prefer `chore(deps):` for dependency bumps; the legacy `deps:` type is also mapped to the Chores section but is being phased out, so don't use it for new commits.

Prefer `chore(ci):` for CI/build-pipeline changes (rather than a bare `ci:`) so they surface in the Chores changelog section instead of being hidden.

### User-facing commits: write the subject for users

When a `fix:` or `feat:` changes something a user can see or feel — UI, download/indexing behaviour, settings, notifications, feeds, anything that shows up in the app or changes how it behaves for them — the subject line (`-m`, the first line) should describe the change in terms of its **user-visible effect**, not the internal mechanics. These subjects flow into the release-please changelog, so someone reading the release notes should understand what changed for them without knowing the code.

- Lead with what the user now experiences (or no longer experiences), not the function/module/refactor that made it happen.
- Keep the Conventional Commits prefix and scope; only the wording after the colon changes in emphasis.
- Put the mechanics (which module, why, how) in the commit **body**, not the subject.

Examples:

- Prefer `fix: correct pending count for sources with no downloaded media` over `fix: adjust MediaQuery pending clause for null download states`.
- Prefer `feat: let sources skip livestreams still in progress` over `feat: add live_status check to indexing filter`.
- Prefer `fix: stop re-downloading videos after a title change` over `fix: use media_id instead of title in download archive`.

For non-user-facing types (`chore`, `refactor`, `test`, `ci`, internal `perf`, etc.), keep writing the subject in normal developer terms — there's no user effect to lead with.

While iterating on a change, run the relevant tests with `tooling/test.sh <path>`
(see the Commands section) to get fast feedback without the full check suite.

Before staging and committing, always run these two checks in order:

1. `prettier . --check --config=.prettierrc.js --ignore-path=.prettierignore --ignore-path=.gitignore --write` — auto-fixes formatting so CI's prettier check doesn't fail.
2. `tooling/lint_test.sh` — reproduces `.github/workflows/ci.yml`'s `test` job (compiler, credo, sobelow, ExUnit, prettier check) inside the same pinned ci-base Docker image, so a green run here means a green CI `test` job. Requires Docker. Run this after prettier and before every commit.
3. If on main branch, create new branch for your commits.

Releases are automated via release-please using semantic versioning (current version tracked in `version.txt`, e.g. `1.2.0`). Merging the release PR cuts a release and publishes Docker images to GHCR and Docker Hub. (`mix version.bump` / `tooling/version_bump.sh` still produce a legacy date-based `YYYY.M.D` version and predate the move to release-please — prefer the release-please flow.)

Never push commits unless explicitly asked to do. I prefer commits amended if the work is related to a new feature or a new fix.
